## Consumption is not an executable grant

The D2 campaign regression explicitly forces `SET CONSTRAINTS ALL IMMEDIATE` after consumption. A deferred constraint trigger can then have completed before subsequent expiry, trusted authority changes or COMMIT. It is not an unconditional durable-commit freshness boundary and must not be described as one. The official adapter still owns one dedicated transaction connection and performs explicit precommit and post-acknowledgment checks; those remain clock samples, not proof of the strict executable contract. Deliberately combining administrator and consumer powers in one test transaction demonstrates why service-role separation is a prerequisite, not a reason to grant execution. Exact committed tombstones/effects/receipts survive late or unknown acknowledgments; no retry is authorized.

PostgreSQL's [SET CONSTRAINTS contract](https://www.postgresql.org/docs/16/sql-set-constraints.html) explicitly includes constraint-trigger timing and retroactive execution when switching to IMMEDIATE; D2 verifies that behavior dynamically.

The fixed `consume_action(ticket, operation_id)` operation consumes a synthetic signed action exactly once under the existing canonical gate. It returns transaction-local diagnostic evidence, never execution permission. The injected adapter explicitly performs BEGIN, consume, a pre-COMMIT check, acknowledged COMMIT and an independent post-COMMIT check on one dedicated connection. Every result has `grant:false`, `canExecute:false` and `releaseAuthorized:false`, including fresh acknowledged consumption and later positive inspection. This is deliberately **not wired into Phase 1F's successful consume callback**: ordinary PostgreSQL cannot prove the strict 1G-A atomic wall-clock freshness contract through commit and acknowledgment. That grant contract remains blocked. No resource action, including read/write/test permits, is implemented; unsupported action types are rejected rather than interpreted as commands.

## Authentication and complete catalog validation

A trusted server verifier uses the existing Phase 1B request/worker-claim Ed25519 formats and the Phase 1F domain-separated host proof. The new signature-only Phase 1F helper preserves its exact scalar snapshot/signature validation and does not change the existing execution/release contract. Independently pinned coordinator, worker and host public keys are required; no caller-selected signing key from an envelope is trusted. Wrong signatures, signed-but-inconsistent request/claim/proof hashes, request ID, worker, host, run/version, time intervals, action or path fail before registration. Proof and claim deadlines are constrained by the signed request. Paths are exact reviewed paths or descendants with a slash boundary; traversal, absolute/dot-segment and prefix-confusion paths are denied.

`ppo_action_verifier` can read a consistent target ownership/catalog snapshot and register an immutable, bounded context attestation. It cannot consume actions, change host policy or mutate canonical state. The verifier validates the **entire** existing catalog/history with the merged canonical validator: no invalid records, missing/extra versions, truncated catalog, duplicate active projects, WIP overflow, normalization or native numeric loss. It hashes the native PostgreSQL JSONB entries text, retained independently of JS parsing. SQL registration obtains the gate and compares that exact digest and both ownership identities/generation against current authority. Consumption repeats the digest comparison under the gate, so any canonical/history change invalidates the attestation, even if an apparent revision or current head is unchanged. The attestation stores signed request/claim/proof scope and a catalog digest, not a second canonical run store.

Signature verification and complete JS history semantics remain a **trusted server role boundary**, as in the existing canonical writer. PostgreSQL does not implement Ed25519 or duplicate the JS state-machine validator. Possession of the verifier role can fabricate an attestation; it must never be granted to a host/client or exposed as arbitrary JSON/SQL. The consumer cannot submit certificate digests or replacement boundary fields: it supplies only the opaque registered ticket and operation UUID. Authenticated transport, role-to-service isolation and production key custody remain prerequisites. Synthetic tests use fresh keys and SET ROLE from a disposable administrator; no production service authentication is claimed.

## One authoritative mutation boundary

No shadow run table is added. SQL reads canonical `current_runs` derived from immutable `run_versions`. The fixed consume operation updates the same singleton gate as `commit_run`, import, source/target commits and ownership transitions. Synthetic host configuration, request/claim revocation and context registration also update that gate first. Gate UPDATE, rather than a row-only read lock, forces stale REPEATABLE READ/SERIALIZABLE transactions to fail with a serialization error. No automatic retry occurs.

Under that gate, consumption independently requires:

- Target phase, exact source/target UUID identities and bounded ownership generation.
- Active `lab-` host, exact pinned host/worker/coordinator key fingerprints, worker and epoch, with the exact claim explicitly pinned to that epoch. Host lifecycle changes use expected-epoch CAS and advance the server epoch on every policy/key/status change; there is no deletion/reset/reactivation with an old epoch.
- Host-specific project and capability grants independently of the request's scope, and the fixed backend/codex or frontend/antigravity capability/worker mapping.
- Exact request/claim/proof digest, request ID, worker/host and run/version bindings. Append-only request/claim revocations invalidate existing attestations.
- Current canonical version, implementation status, project, branch, base and head SHA, exact complete certified catalog, no more than two active projects and one active run per project. The implementing target run itself must retain its active lane.
- Exact supported diagnostic action and repository-relative workspace path scope.
- All not-before/expiry bounds and a unique durable `(host_id, action_id)` tombstone, also uniquely bound to ticket and operation UUID.

Tombstones retain context hash, authority identity/generation, host epoch, consume time, immutable deadlines and transaction identity. Contexts, revocations and tombstones are append-only, protected by triggers and ordinary-role permissions; direct INSERT/UPDATE/DELETE/TRUNCATE/replacement is denied. Only fixed functions are granted, with pinned search paths and no PUBLIC execution. The final deferred trigger also rechecks bindings, preventing a trusted same-transaction authority change from silently preserving a grant diagnostic. Privileged administrators, schema replacement and restored backups are outside this protection; anti-rollback identity/restore policy remains mandatory.

## Freshness observations and unavoidable gaps

All authoritative samples use PostgreSQL `clock_timestamp()`, which changes within a statement, unlike transaction-start `CURRENT_TIMESTAMP` ([PostgreSQL 16 clock semantics](https://www.postgresql.org/docs/16/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)). Checks occur after obtaining the gate, in the nonce INSERT predicate, after insertion, in the explicit pre-COMMIT operation, in a deferred constraint trigger, and after acknowledged COMMIT. Complete catalog/binding work precedes the final samples in the pre/post checks and deferred trigger. Post-ack evidence must retain the exact operation, context hash and ownership identity/generation and cannot regress from the adapter's pre-COMMIT microsecond clock sample. Observed expiry/regression/stale binding/unavailable evidence denies even a diagnostic freshness acknowledgment.

A deferred trigger runs before transaction completion, not at an atomic wall-clock durable-commit instant ([PostgreSQL constraint triggers](https://www.postgresql.org/docs/16/sql-createtrigger.html)). WAL flush, synchronous replication, another deferred trigger, socket delivery, scheduling and caller observation may occur later. PostgreSQL clocks are wall clocks, can step, and are not a distributed monotonic clock proof. Unobserved clock steps and rollback/restore are not solved. The adapter's last sample precedes response delivery. Therefore these checks establish **sampled freshness and durable diagnostic consumption**, not an atomic wall-clock commit/ack grant. Tests intentionally delay actual COMMIT after the final freshness trigger and demonstrate that the tombstone may commit after expiry: the post-ack read denies and retains it. No strict 1G-A success is claimed.

Expiry observed before commit rolls back. A late or uncertain acknowledged outcome denies and never deletes a committed tombstone. `unknown` includes lost COMMIT response, failed connection and malformed/rebound evidence; it is not proof of rollback. Each adapter instance allows only one attempt, including failed BEGIN. A new instance cannot bypass durable nonce uniqueness. The caller must choose/persist `{ticket,operationId}` before dispatch when crash recovery is required; UUID generation by the convenience call is not a production outbox. The restart test fsyncs an operation journal and a new Node process independently inspects it. Inspection of exact positive evidence reports `consumed` while still denying any grant; missing evidence reports `unknown`, never noncommit or retry permission. An in-flight transaction may still commit. No retry, tombstone pruning, target reset, filesystem fallback or old-source revival exists.
