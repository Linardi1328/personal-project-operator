## Corrected integrated profile

The existing foundation scripts remain independently testable storage primitives; they are not a D1 admission service. The integrated laboratory must install `admissionProfileSql()` after canonical/import/catalog and before service access, using `{ownership:true}` when the ownership module is present. This static repository SQL loader installs the admission and ownership fragments in one transaction. `admissionOwnershipSql()` atomically adds the ownership module and its integrity wrapper to a direct D1 lab. These helpers return fixed SQL only; no production driver, route, migration runner or generic SQL endpoint is installed. Installation is for fresh disposable labs, not a claim of safe live upgrade/quiescence with in-flight legacy callers.

`createCatalogCertifiedQuery({mode:"isolated-catalog-certified-authority",query,verifierQuery})` wraps the existing fixed canonical, source, target, bootstrap and import seams. The ordinary read/mutation transport and separately scoped verifier transport are captured as trusted server infrastructure. Neither capability may come from request JSON or a host. Missing profile functions, unavailable validation or failed acknowledgments deny; there is no fallback to a foundation writer or filesystem.

Preparation reads native current records **and every historical version**, or the source's complete normalized record/marker corpus, in one PostgreSQL snapshot. It constructs the exact prospective current-record replacement and new historical marker, or full bootstrap/import corpus. Both existing and prospective snapshots pass the existing complete semantic catalog validator: record/history/hash/identity/recovery checks, unique decoded keys, exact native numeric values, complete contiguous markers, WIP and the existing 20-run readiness rule. Fresh serialized submissions and normalized import inputs are checked for duplicate decoded keys before PostgreSQL normalization. Legacy raw archive last-key-wins compatibility and exact raw bytes remain unchanged.

A token hashes the authority installation UUID, current gate revision, operation kind, complete candidate/request (including expected CAS hash/version and original serialized text), native existing/prospective entries and ownership identity/generation/phase/manifest metadata where present. Private source/target permits are not returned in preparation snapshots. The opaque hash is attested only by `ppo_admission_verifier`; ordinary writer/importer/source/target roles cannot register certificates or write the certificate table. A token is not a client assertion or executable grant. The trusted verifier role can lie, as with the existing trusted semantic writer; authenticated service-role isolation and key/transport custody remain production prerequisites.

All public mutation names acquire the **existing gate row lock**, independently reconstruct the native preparation and require its exact attested token before calling private fixed CAS/import/ownership implementations. Core gate UPDATE still advances the revision and aborts stale REPEATABLE READ/SERIALIZABLE transactions. A changed catalog, candidate, revision, installation identity or ownership state invalidates certification. Even a gate-only change conservatively makes the old certificate stale. There is no automatic recertification/retry. Validation and verifier calls occur before acquiring the mutation lock; only native SQL revalidation executes under it.

The old names `commit_run`, `import_synthetic_snapshot` and ownership wrappers cannot bypass certification after profile installation. Their renamed private implementations lose ordinary execution grants. Fixed import and target batches invoke private CAS implementations only after whole-operation certification; the existing independent CAS/history/WIP/byte/archive checks remain. D1 does not grant direct writer/import privileges when ownership is already installed. Direct bootstrap remains valid in a direct authority; source bootstrap remains valid only through the exclusive ownership path. Source-only abort, freeze, activation and other non-admission control operations retain their existing fencing checks and do not require a target catalog certificate. An invalid/truncated quarantined target therefore cannot prevent a valid source-only abort or source admission based on its own complete source corpus.

## One prospective capacity policy

The readiness ceiling remains **20 total current runs**, including cancelled/completed histories. WIP lanes are a separate constraint. Cancelling/completing a run frees its active lane but does not erase its history or free a total-run slot. At 20 runs, valid progress, transitions and cancellation remain possible if all other bounds permit. A 21st run is denied atomically, including concurrent contenders.

SQL independently enforces total-run capacity, the existing per-run versions 0..99, at most 2,000 historical versions, native physical/serialized aggregate limits and WIP. Current-record and historical-version representations both count toward byte limits: appending a version retains all old markers, replaces the current representation and adds the new marker. Prospective snapshots include both copies. Native preparation uses bounded count probes before aggregation and fails closed when existing native data cannot fit. Incoming normalized files are individually bounded before JSONB expansion and checked cumulatively before building a large result.

The complete physical/native serialized snapshot budget remains 32 MiB (including conservative metadata overhead); normalized logical validation retains its existing 32 MiB aggregate and 128 KiB record limits. The existing per-candidate physical JSONB cap remains 8 MiB. Source-specific 4 MiB raw and separately normalized totals, 128 KiB per file and 2,100-file ceiling remain stricter; the coherent 20-run/100-version policy implies at most 2,020 canonical current/marker entries. Imports must also fit each existing CAS replay step's independent bounds; certification cannot bypass them. Combined preparation transport is bounded to 70 MiB for two 32 MiB snapshots plus metadata. The disposable large-snapshot test transport has explicit 60-second client and 45-second server deadlines; ordinary test statements retain 20/15-second deadlines. A push runner reached the old 20-second transport deadline while a separate PR run passed; this test allowance is not a production resource budget. Accepted-input/result bounds are not process-memory, CPU/I/O or query-cost ceilings.

At per-run version 99 or aggregate history/byte exhaustion, further appends—including progress or cancellation—deny without partial history/archive writes. There is no exception that prunes markers, rewrites history, resets authority or raises limits. A pre-existing invalid/over-capacity catalog cannot bootstrap new work or be silently repaired by admission. A separately reviewed remediation/policy change is required. Source-only ownership abort remains a non-admission operation under its original rules.

Certificates retain only hashes, not a shadow canonical run store. A separately serialized monotonic certificate budget limits storage to 10,000 issued slots; concurrent duplicate registrations can conservatively consume extra budget but cannot exceed it. No automatic pruning/reset exists. Certificate acknowledgment failure never permits automatic mutation retry; unknown mutation acknowledgments retain the original conservative canonical/ownership reconciliation contracts. A positive exact receipt can establish commitment, while absence cannot establish noncommit.
