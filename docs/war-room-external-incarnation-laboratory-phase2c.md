# RIC-157 Batch 2C — external incarnation witness preparation

Base: merged D1 `3207553da0c301adb04618f1b71fa20bbfecf90b`. This independent slice is a bounded external witness and a disposable PostgreSQL restore/clone laboratory. **Batch 2C remains incomplete.** Existing canonical, admission, ownership, action and resource SQL entrypoints do not consult this witness. A test deliberately demonstrates that raw SQL after restore can consume an old action again; the private controlled test adapter rejects that same rollback. No whole-system anti-rollback guarantee follows from this component.

The owner approved the architectural direction at Batch 1 revision `762e6d622b8ce1980675768c03f0299928e2cc39`, subject to remaining proof gates. That approval requires the final freshness check to account for durable journal-reservation delays. Recovery of an unaccepted prepared operation must never authorize its first native effect after expiry. Five seconds remains only a candidate ceiling: concrete clock uncertainty, duration and cancellation budgets require measured evidence and separate approval. This slice neither implements a native resource boundary nor changes executable semantics. All results retain `grant:false`, `canExecute:false`, `releaseAuthorized:false`; no successful Phase 1F callback, merge or pilot is enabled.

## External trust and durable state

`local-operator/development-external-incarnation-anchor.mjs` requires explicit isolated mode, an absolute canonical path, and independently pinned anchor, authority and owner UUIDs. Its directory must be owned by the current service UID with mode 0700, outside **every** restored/cloned PostgreSQL or resource snapshot. The external anchor itself must not be rolled back. This assumption requires independent OS/service custody; putting the directory beside a database backup does not establish it. No production accounts, credentials, enrollment or network service are introduced.

An exclusive `service.lock` directory permits one local witness process. Every mutation checks the pinned root, record-directory and lock-directory device/inode, ownership, restrictive permissions and canonical nonsymlink path. Record files use exclusive create and `O_NOFOLLOW`, mode 0600, one link, bounded bytes, canonical JSON, ordered sequence numbers and a SHA-256 chain. A record is acknowledged only after its file and record directory are fsynced. Each transition retains the authority/owner identity, monotonic incarnation, service instance UUID, complete database checkpoint, exact pending operation and bounded previously reserved operation/subject identities. Positive commit records also durably retain the exact receipt digest. This journal contains evidence, not an execution credential.

The component denies partial records, sequence gaps, malformed transitions, altered bytes, symlinks, directory substitution, changed identity and exhaustion. It neither repairs nor truncates the journal. Its path checks detect substitutions at checked boundaries; they are not an openat-style containment proof against an adversary already running as the witness UID. The owner-only directory and absence of hostile same-UID writers are prerequisites. A privileged host attacker, rollback of the external anchor, cloned service credentials or a malicious trusted adapter are outside this component's proof.

The persistent lock survives process death. There is no timeout, stale-lock deletion, reset, takeover or replacement-owner endpoint. A crash or uncertain storage write can therefore make this witness permanently unavailable through the current API. That is deliberate quarantine, not a recovery implementation. Enabling recovery requires an independently proven fence against the old owner and a separately reviewed protocol. Directory checks and hashes alone cannot prove that an unreachable old owner stopped.

Graceful close is serialized through the same queue as inspection and mutation. A close-first reservation denies as closed, and concurrent closes are idempotent; shutdown cannot race a second append to the same journal sequence. A close ordered after a pending reservation still retains the persistent lock.

## State and operation ordering

Initialization and every clean reopen begin quarantined. Explicit activation requires the current complete database checkpoint and exact current witness record hash; it advances the external incarnation and creates a fresh instance UUID. The fixed pinned owner cannot change. An old incarnation or instance, another authority/owner, a stale checkpoint or a reused operation/subject denies. Initial enrollment is trusted local test administration, not untrusted self-enrollment.

The witness allows exactly one pending immutable operation. Reservation binds its UUID, one of two fixed diagnostic kinds (`consume-action`, `revoke-host`), subject digest and exact input digest to the current external binding and checkpoint. Reservation is durably written before the private adapter issues its fixed PostgreSQL operation. It immediately quarantines the witness, so a second effect cannot be prepared. No arbitrary callback, SQL statement, command or filesystem mutation is executed by the witness. A returned reservation is diagnostic evidence and must never become a transferable execution permit.

The private adapter exists only in the integration test. It calls the existing `consume_action` and `configure_action_host` functions, reads exact positive durable evidence and binds the resulting complete checkpoint and receipt digest back to the pending reservation. Its checkpoint hashes native PostgreSQL text for **every actual table** in `ppo_authority`, including canonical history, gate and ownership, host policy/epochs, contexts, revocations, tombstones, resource operations/versions/receipts, admission certificates and imported archive evidence. Aggregation uses one SQL snapshot and preserves native numeric values. A revision/count-only preflight would not suffice. Schema/function attestation and protected production query access remain separate integration requirements.

The test adapter does not expose an operation until its witness reservation is durable. Existing SQL freshness checks therefore occur after reservation I/O; they remain diagnostic samples with the original strict freshness blocker. This is not a proof of the proposed native final acceptance boundary. Any future native implementation must stage/reserve first and then perform its conservative final clock check before conditional publication.

A lost response leaves the exact pending operation latched. Reconciliation only reads the exact existing tombstone and current checkpoint, then records matching positive evidence. It never invokes consumption, host configuration or any native effect. Missing/contradictory evidence cannot clear pending state or establish rollback. Closing with pending work retains the persistent lock. A positive reconciliation still returns quarantined evidence; a separate exact activation is required before another reservation. No automatic retry, new-ID duplicate, history pruning or permissive fallback exists.

## Evidence and limits

Unit tests use real local disk and a killed child process. They cover durable reopen/incarnation change, old bindings, concurrent opening, reinitialization, one pending identity, exact commit evidence, retained operation/subject uniqueness, all pinned identity mismatches, changed/partial journal data, symlink and directory substitution, permissive permissions, process death and bounded history exhaustion.

The separate `phase2c-external-incarnation.integration.mjs` suite installs the existing D1-certified ownership/action/resource fixture in a network-none disposable PostgreSQL container. It uses actual `pg_dump`/restore and a separate cloned database to test:

The explicit CI driver runs this self-cleaning suite before the legacy canonical suite. The legacy suite intentionally retains its last fixture until container teardown; appending another fresh installer afterward caused the retained first full-CI `role already exists` failure. Running the self-cleaning suite first preserves both suites and requires no reset of a predecessor's fixture.

- A restored snapshot loses consumed nonce and host revocation in PostgreSQL; the unchanged external checkpoint/reservations reject the old action without a new mutation. A raw SQL rollback control demonstrates the remaining bypass honestly.
- A clone has copied database identity/data but no separately enrolled external owner; it cannot use or reinitialize the existing witness. Protection against copying privileged service identity is not established.
- A committed action with a lost response remains pending until exact positive tombstone reconciliation, with no effect replay.
- Restoring a snapshot which lacks that outstanding positive outcome cannot reconcile it or admit a replacement owner.

A further expiry control first proves fresh consumption in a rollback-only transaction, then durably reserves the exact operation and waits past its deadline before the fixed SQL mutation. Consumption denies with no tombstone; read-only recovery cannot create the first effect or clear the pending reservation. This demonstrates the diagnostic adapter's ordering after reservation and preserves the owner's additional condition; it is not a native filesystem/Git final-acceptance proof.

Retained limits: 128 immutable records, 16 KiB per record and 32 reserved operation/subject identities. Exhaustion denies without deleting evidence. These are laboratory capacity bounds, not a production lifetime policy, measured performance budget or permission to prune/reset. A graceful close also needs one free record; if exhausted it leaves the lock quarantined. Disk durability assumes successful filesystem fsync semantics and suitable underlying storage; this slice does not certify hardware power-loss behavior.

## Required integration before complete 2C

The separately developed Batch 2B service component uses fixed authenticated verifier/consumer/admin endpoints. A future reviewed integration must bind the external incarnation, instance, owner and exact witness operation into every accepted action/resource request and authenticate them independently. This branch does not import that unmerged component or claim combined verification. The local injected fixed SQL adapter and owner UUID test are not mTLS identity/key-custody proof.

Every canonical, import, admission, source/target, ownership, host/key/epoch, request/claim, global-stop, action and resource mutation gateway must participate at its actual mutation boundary, including uncertain connection disposal, process restart and restore/clone startup. A cached unsigned witness preflight cannot protect a later raw SQL write. Dedicated service permissions must prevent clients from bypassing the gateway or selecting another owner. A protected native resource must independently enforce the owner/incarnation fence; witness process exclusivity alone does not fence a filesystem or Git service after connection loss.

Outstanding operations need an approved recovery protocol, positive native evidence, external-owner fencing and a capacity/retention policy before any reinitialization or takeover. No native resource enforcement, authenticated full integration, anti-cloned-key protection, automatic stale-lock recovery or real Mac/VPS readiness is claimed here. RIC-157 remains In Progress; RIC-59/RIC-61 remain held. Actual hosts, connectivity/enrollment, live credentials, dispatch, production migration/routing/deployment, factory cycles, retirement and a controlled pilot remain unauthorized.
