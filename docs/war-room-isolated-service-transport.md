# RIC-157 — isolated pinned service transport component

Base: merged D1 `3207553da0c301adb04618f1b71fa20bbfecf90b`. This is an independent Batch 2B component in the pilot campaign, not a production service, installer, enrollment API or complete pilot-readiness claim. It opens only explicit disposable loopback listeners. RIC-157 remains In Progress; RIC-59/RIC-61 remain held. No merge without owner approval.

`createIsolatedPinnedService` and `createIsolatedPinnedClient` require the literal mode `isolated-pinned-service-transport-only`. They use native Node HTTPS/TLS 1.3 with mutual CA validation **and separately pinned SPKI SHA-256 identities**. Certificate common names and client JSON do not assign authority. All responses retain `grant:false`, `canExecute:false`, `releaseAuthorized:false`; successful Phase 1F execution remains disconnected. Neither this transport nor an authenticated diagnostic response relaxes executable freshness or authorizes a later external mutation.

## Service and database boundaries

One service instance accepts exactly one service type and that type's fixed capability set. Verifier, consumer and administrator have separate TLS identities. An authenticated coordinator can call verifier/consumer operations; only a separately pinned administrator identity can call the administrator service. Giving a consumer service an administrator factory fails construction. The transport never accepts SQL, a database role, a caller-created verifier certificate, a command or a replacement pin in a request.

| Service | Fixed POST route | Exact top-level input |
| --- | --- | --- |
| Verifier | `/v1/action/register` | signed request, claim, proof and an already chosen ticket UUID |
| Verifier | `/v1/resource/context` | ticket UUID; bounded native resource/context read |
| Verifier | `/v1/resource/register` | separately signed resource descriptor and exact payload |
| Consumer | `/v1/action/consume`, `/v1/action/inspect` | ticket and operation UUID |
| Consumer | `/v1/resource/apply`, `/v1/resource/inspect` | ticket, operation UUID, descriptor hash |
| Administrator | `/v1/host/configure` | synthetic host ID, expected epoch, bounded policy |
| Administrator | `/v1/context/revoke` | exact request/claim kind and digest |

The verifier calls the existing full signed action/history validator and separately signed resource descriptor validator with independently supplied coordinator/worker/host keys. It does not register client-supplied attestations. Consumers invoke the existing fixed transaction adapters, including pre-COMMIT/deferred/post-ack checks. Exact inspection remains read-only and never permits retry. Host administration delegates only to the existing fixed CAS/append-only functions. Context/host policy semantics and canonical ownership/WIP/catalog enforcement remain in PostgreSQL, under the unchanged shared gate.

Every request obtains a new, exclusively owned server connection from the selected trusted factory. Before any mutation it checks PostgreSQL `current_user`, `session_user`, both roles' privileged attributes and exact direct login membership. The expected LOGIN is `ppo_transport_<capability>` and belongs only to its matching existing NOLOGIN role. Superuser/create-role/create-database/replication/BYPASSRLS logins, wrong current roles and expanded direct membership deny. Session object reuse also denies. Only the relevant compiled statement constants and transaction commands can reach that connection. An ordinary client cannot select a different factory or switch roles.

The transport itself supplies no production driver, database URL or credential. Factories are trusted server infrastructure, not request callbacks. Actual deployments would need separate low-privilege processes/accounts and authenticated database connections; a role label returned by an arbitrary fake callback is not proof of those properties. Tests exercise the query boundary both with controlled fakes and actual PostgreSQL LOGIN roles. The disposable container uses its private local socket authentication; this does not establish production database authentication or OS/service-account isolation.

## Pin lifecycle, attempts and ambiguity

The trusted registry starts from independently supplied identities/pins. Each rotation or revocation requires expected-epoch CAS, advances a monotonic epoch and retires the old pin. Retired pins cannot be reassigned. A service checks the current peer/service pin at request entry, before each database statement and before responding. Rotation/revocation cancels affected active attempts and disposes their connections. Clients check the server's current pin before sending and again when accepting the response. Replacing a server key requires a matching trusted registry update and a service using the replacement credential; a CA-valid certificate alone is insufficient.

TLS transport identity rotation is separate from Phase 1F Ed25519 host/coordinator policy and host epochs. It does not automatically enroll a host, transfer a claim or rotate a database host policy. Those independently pinned bindings still must pass the existing signed verifier and SQL checks. This component's bounded registry is process-local synthetic policy. It does **not** prove persisted revocation, safe restart/restore, external incarnation anchoring or exclusive authority after clone. Those Batch 2C/key-custody integrations remain blockers.

Each client object permits one network attempt, including validation/connection failure. There is no network, SQL or mutation retry and no pooled connection return. Every server attempt disposes its connection on completion, error, timeout, malformed evidence or HTTP disconnect; disposal must terminate/close the actual driver session. A factory which wraps a reused or privileged session violates the contract. Connection loss can occur after COMMIT: disposal does not erase a committed tombstone/effect/receipt. Unknown acknowledgment remains `unknown`; a new explicit exact inspection may report positive committed evidence, never noncommit from absence or permission to repeat. Administrator acknowledgment uncertainty similarly requires trusted reconciliation, not repeating a configure/revoke call. No generic administration inspection endpoint is added.

The client snapshots the exact serialized JSON before dispatch and binds its response to that private snapshot, so caller mutation cannot rebind acknowledgment identity. Cancelled connection factories retain their request-capacity slot until a late connection is disposed; four stuck factories close admission rather than allowing unbounded additional openings. Trusted factories and disposal still need independently enforced driver deadlines. TLS handshakes have an explicit two-second timeout, and header deadline checks run at a bounded configured interval; event-loop scheduling and real operating budgets remain unproved. The login probe checks all direct and transitive memberships; a single direct consumer grant cannot conceal a parent administrator role. A real PostgreSQL negative probe grants that transitive role, proves denial before consumption, revokes it and proves the original action still succeeds.

Cancellation and cleanup share one disposal promise. The attempt retains its capacity slot until actual disposal settles; a rejected disposal quarantines that slot rather than assuming the connection closed. Shutdown cancels work, closes sockets and waits for current attempt cleanup within an explicit ten-second drain budget. Failed or unsettled cleanup reports uncertainty and does not certify termination, noncommit or restored capacity. A trusted driver whose disposal never completes remains an operational blocker. A prior committed synthetic effect is never rolled back by shutdown reporting uncertainty.

A registry update can race already-dispatched PostgreSQL COMMIT. Rechecking pins or destroying the socket cannot prove that transaction did not commit. Transport revocation prevents new work and cancels observed in-flight attempts; it is not an instantaneous wall-clock rollback guarantee. Existing immutable nonce/resource/receipt reconciliation and all false grant flags remain essential. The original strict executable commit/ack freshness blocker is unchanged. Owner approval of proposed protected-resource semantics at `762e6d622b8ce1980675768c03f0299928e2cc39` does not activate this transport: concrete clock/duration/cancellation budgets and all resource proofs remain separate gates. Final resource authorization must occur after durable journal-reservation delays, and recovery of an unaccepted prepared operation must never cause its first effect after expiry. Inspection here remains read-only.

## Explicit component bounds

Requests and responses are at most 64 KiB; UTF-8 and JSON are strict, decoded duplicate keys deny, nesting is at most 32. Two legal 4096-byte resource values can expand to 49,152 bytes together under six-byte JSON escaping, plus bounded receipt/evidence metadata. A bounded 32 KiB action context plus one escaped resource also fits this response ceiling. The prior 16 KiB response cap was reproduced as an inability to inspect a committed legal payload; the real PostgreSQL regression now commits and exactly reconciles two maximum escaped values, including the complete before/after receipt. This is a derived wire bound, not a raised payload, time or production budget.

Only POST/application-json with bounded explicit Content-Length is accepted; compression and transfer encodings deny. Unknown routes, surplus top-level fields and unsupported operations deny. A service admits four active requests and sixteen sockets, with two-second header/body budgets, a ten-second overall operation budget and a twelve-second absolute client budget. All waiting/uncertain connections are discarded. No deadline is silently enlarged to fit a large catalog; a valid operation which cannot finish within this component budget fails closed.

The registry holds at most twenty initial identities and 128 retired pins; epochs are bounded below one billion. Exhaustion denies without reset or pruning. These are test/component limits, not measured production budgets. A verifier can still read the existing large native catalog through its private driver; transport byte caps do not bound Node/PostgreSQL peak memory or database scan cost. Original M-03 measured latency/plans, lock/revocation delay, memory, connection/concurrency, disk/WAL, cancellation, timeout and retention policies remain mandatory. The 20-run laboratory ceiling is not silently adopted as a production lifetime policy.

## Verification and remaining integration

Unit tests use real loopback mutual TLS, fresh disposable RSA-2048/SHA-256 test certificates and separate pinned client identities. They cover current/rotated/revoked pins, CA-valid wrong service identity, principal/service separation, SQL/role/attestation injection, duplicate/malformed/oversized inputs and outputs, privileged/wrong-role membership probes, bounded concurrency, connection disposal and lost acknowledgment with no automatic retry. Database callbacks in these unit tests prove transport behavior only.

The dedicated PostgreSQL integration cases install D1, create separate nonprivileged LOGIN roles with one matching NOLOGIN membership each, and connect as those logins before selecting their single granted role. Real HTTPS clients drive signed action verification/consumption/inspection and separately signed synthetic resource registration/CAS/receipt inspection. The targeted real PostgreSQL run passed all four subcases (five reported tests including the parent). The first run caught a new test-driver error wrapping SET ROLE in SELECT (42601); it is preserved in the campaign evidence, and the corrected direct statement now requires and receives 42501. Tests check exact atomic resource/version/receipt/nonce counts, lost committed acknowledgment and positive reconciliation, HTTP disconnect killing a real in-flight session with rollback, no automatic retry, and actual SQLSTATE 42501 for unauthorized role switching/private helper calls. The original canonical/native/archive and action/resource tests remain unchanged and run in the complete CI suite.

This is not whole-Batch-2B completion: production database authentication and process/account separation, durable authenticated pin lifecycle and external restore/incarnation anchoring, protected source/resource gateways for every relevant writer, measured operational budgets and key custody remain unproved. Existing raw laboratory SQL/adapters are not globally routed through this listener. Enabling those raw capabilities outside a protected service can bypass transport and must remain prohibited in any pilot configuration. Combining separately tested components without exact integration proof is not readiness evidence.

No real credentials, host enrollment, Mac/VPS connectivity, dispatch, filesystem/Git effect, generic command runner, production routing/migration/deployment, retirement, hold release or factory cycle is introduced. Any approved resource authorization proposal still requires separately reviewed implementation, all dependency proofs and distinct final pilot authorization.
