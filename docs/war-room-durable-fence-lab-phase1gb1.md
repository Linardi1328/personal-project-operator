# RIC-157 — Phase 1G-B1: durable transaction laboratory

**Scope:** isolated single-host SQLite experiment, not the final shared authority, a production migration, or a live authorization service. This is a new implementation slice after the merged 1G-A contract and trusted Mac enrollment design.

## Why this slice exists

PPO's current development-run-state.mjs is file-authoritative: commitRecord writes an exclusive durable version marker first, then writes the canonical JSON record. readDevelopmentRunInternal may repair JSON from the newest authoritative marker. Creation, transition, progress and recovery can all write through these primitives. development-run-catalog.mjs inspects the separate filesystem records and history. A database transaction that locks only a nonce table while reading that live file store would have a check/use race. Neither a mirrored run row nor a process-local lock fixes it.

This laboratory uses only fresh synthetic run records generated using PPO's existing state-machine APIs in a disposable scratch directory; that scratch directory is deleted before the database is populated. The laboratory database is the **sole** authority for those synthetic records, never a second writable copy of real PPO state. It validates full records including history with parseDevelopmentRunRecord, derives WIP membership using the current admission policy, and rejects duplicate active runs per project, corrupt or incomplete catalog state and more than two active projects. This is not yet full production catalog/recovery validation: the laboratory scans up to 100 complete records directly, whereas the current production catalog also denies truncated 20-summary presentation results and detects filesystem version-marker/record recovery inconsistencies. The laboratory has no separate version-marker store. Phase 1G-B2 must explicitly preserve the recovery-denial policy and distinguish authoritative completeness from display pagination.

## Implemented experiment

- Node's built-in SQLite (Node 22.13+ with node:sqlite and SQLite subsecond clock support; POSIX only). No external packages, service, credentials, migration of real data or new production process.
- Fresh private temporary directory and database, random lab marker, schema version/application ID check, explicit reopen; no environment-selected or caller-provided production database path. The trusted local fixture writer exists only in the test file. Lab host IDs are prefixed lab- and run records must have a synthetic task label. A database with more than one hard link is rejected. This is accidental-use isolation under a trusted local filesystem, not protection against a malicious local administrator or arbitrary code with access to the test database. Path checks do not bind a checked inode atomically to SQLite's later open, and WAL/SHM sidecars are not independently authenticated. Metadata is verified after opening the candidate database; do not treat it as proof of isolation from hostile path substitution.
- Separate tables for synthetic host, claim, request, full run records and consumed action IDs. STRICT tables, matching record keys, unique (host_id, action_id) and immutable nonce triggers. The BEFORE INSERT duplicate-key guard ignores attempts to replace a consumed row, including INSERT OR REPLACE on another connection with recursive triggers disabled. UPDATE/DELETE are blocked; recursive triggers are also enabled and checked on laboratory connections. This protects ordinary SQL mutation paths, not privileged schema changes, file replacement or restoring an older database. Schema version 2 rejects old disposable labs rather than migrating them. Host project/capability allowlists are checked independently of request scope.
- BEGIN IMMEDIATE serializes writers to the same local SQLite database; WAL, synchronous=FULL, no automatic retry on contention. The 1G-A adapter runs within this actual transaction. The final insert uses SQLite's current subsecond clock in its predicate and a unique constraint; JavaScript does not manufacture a successful insert.
- Check freshness before commit and again after acknowledged COMMIT using SQLite time. Finish all database cleanup, including potential WAL checkpoint work during close, before deciding whether to return a successful local diagnostic acknowledgment. The last guard observes Date.now() in the same trusted single-host wall-clock domain, compares it to the most recent database clock and the original immutable deadline interval, and denies if it regresses or is expired. This supplemental guard never replaces the conditional database INSERT or pre/post-COMMIT checks. If expiry is detected before commit, roll back; if COMMIT succeeds but expiry or ambiguity occurs afterward, **deny the grant and retain the tombstone**. The final local clock observation is the laboratory's acknowledgment decision, not an atomic wall-clock storage guarantee or a guarantee about when a later caller observes the result. Observed regression denies, but unobserved clock steps and cross-process/host monotonicity are not established. Actual side effects must independently fence expiry and revocation.
- No filesystem/Git action gateway, dispatch, production route, enrollment or agent launch. The callback returns only the existing offline diagnostic success; Phase 1F still denies execution and release. No live callers are wired to this lab. The exported transact(callback) is trusted internal laboratory infrastructure, not an independently authorizing API: direct callbacks can bypass the adapter's full validation and a callback that never settles can hold the writer lock. Production must expose a fixed authenticated server-side operation with bounded transaction execution and cancellation, not accept executable callbacks from untrusted callers.

## Verification

Run `node --test local-operator/software-factory-remote-sqlite-fence-lab.test.mjs` on supported Node. Full regression CI discovers the new test. Tests use real database files and separate Node processes: uniqueness after reopening, competing consumption, writer exclusion, SIGKILL before commit with rollback/recovery, lost response after real commit and replay denial, revocation and changed run version, host-policy denial, invalid/incomplete catalog and WIP overflow, real clock expiry before commit, late acknowledgment during actual COMMIT or connection cleanup (injected native-call latency, committed nonce retained), replacement resistance with recursive triggers disabled, valid rotated-epoch replay denial with a fresh-action positive control, and rejection of non-lab paths/tokens, wrong application/schema metadata and hard-linked databases.

This establishes only the tested single-host behavior. A subprocess kill is not a power-loss, filesystem-corruption, backup/restore or distributed-partition test. The tests use trusted synthetic row writers and disposable tokens (not real credentials); subprocess fixture arguments are not a production secret transport. The laboratory still depends on a supported Node/SQLite runtime; current CI uses its runner-installed runtime. Test timing and subprocess cleanup remain scoped local checks, not a production liveness guarantee. The test uses trusted synthetic row writers; no production database roles, tenant policy, monotonic host-lifecycle service or full signed-envelope integration are implemented.

## Next integration gate (Phase 1G-B2)

1. Inventory every canonical store writer and reader, including creation, version markers, transition/progress/recovery, catalog, admission, cancellations, dispatch/recovery/remote delivery and maintenance. Use a storage boundary that preserves full record/history validation and existing CAS/append-only semantics.
2. Select a **server-owned, shared** transactional authority with independent credentials/permissions, schema migrations and server-side authorization. Move canonical run/history, host/claim/request, catalog/admission and nonce authority into one reviewed transaction domain (or prove an equivalent fencing protocol). SQLite WAL on a network share is not this architecture. The lab is not a backend selection.
3. Prove migration on synthetic snapshots: immutable provenance, exact run/history/hash/version parity, no invalid records lost or invented, explicit ownership handoff, and no remaining writer to the former canonical store. Never dual-write independent authorities. No live migration without separate owner approval, verified quiescence, backup/restore and rollback evidence. In particular RIC-59 and RIC-61 remain holds.
4. Prove authoritative current-time and commit/ack expiry semantics, serialized revocation and host policy, durable nonce uniqueness, fail-closed partitions, crash/restart and ambiguous outcomes with independent clients. Prove database privileges and server-only mutations; connect Phase 1F to the real authority only after these gates. Actual filesystem/Git/other mutations must independently honor revocation and fencing at their linearization points. Disable unsupported action types.
5. Only later implement reviewed enrollment and a separately approved controlled Mac pilot. No production execution is authorized by merging this slice.

Review gates: exact-head CI, CodeRabbit or documented independent review substitution, owner approval and squash merge. RIC-157 stays open until the real shared authority integration is delivered. No change to RIC-59/RIC-61.
