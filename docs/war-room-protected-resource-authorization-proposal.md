# RIC-157 — proposed protected resource authorization contract

**Status: proposal for explicit owner approval; no executable authorization change.** Based on merged D1 `3207553da0c301adb04618f1b71fa20bbfecf90b`. This document is Batch 1D of the pilot readiness campaign. It does not approve the campaign's controlled pilot, implement a resource gateway or establish production readiness. RIC-157 remains In Progress; RIC-59/RIC-61 remain held. Source merge requires owner approval separately from approval of these semantics.

Until the owner approves a specific revision of this proposal **and** its subsequent implementation and adversarial verification are accepted, all existing outcomes retain `grant:false`, `canExecute:false` and `releaseAuthorized:false`. The successful Phase 1F consumption callback remains disconnected. Existing [Phase 1F](war-room-host-action-fencing.md), [strict Phase 1G-A](war-room-transaction-fencing-phase1g.md), [B2c1](war-room-postgres-action-fencing-phase1gb2c1.md), [B2c2](war-room-resource-fencing-phase1gb2c2.md) and [D1](war-room-admission-integrity-phase1gd1.md) contracts remain authoritative; this proposal does not reinterpret them retroactively.

## Proposed condition and scope

The proposed replacement condition is: **one immutable, reviewed operation may be authorized before its deadline at its actual protected resource boundary, then finish or reconcile under that same operation identity.** Authorization is inseparable from the resource owner's conditional effect. It is not a transferable grant to a worker, a general lease to execute commands or permission to perform another effect after expiry.

The initial implementation should choose one small operation, then review the other separately:

- Create one immutable scratch artifact under an owner-controlled fixed directory, with expected state `absent`. The bounded native artifact binds the operation UUID and exact payload digest. Publication must use a proven exclusive native create/publication primitive, with complete staged contents; opening an empty public file and subsequently writing it does not provide atomic publication.
- Advance one fixed scratch Git ref from an exact expected old object ID to an exact reviewed new commit object ID. The permitted commit binds the operation UUID and expected predecessor. The resource owner uses Git's expected-old-ref compare-and-swap; a supplied canonical head or a prior `rev-parse` is not actual resource state or a CAS.

No arbitrary path/ref, file replacement, recursive edit, shell/test runner, network effect, project repository, production credential or generic Git interface is authorized. Supporting file replacement would require a separate native CAS/recovery proof. No operation spans both a filesystem artifact and a Git ref as one atomic effect. Unsupported semantics deny.

## Exact boundary and identity

Each resource has a protected native identity and incarnation, an ordered fence value, and authoritative state owned by a dedicated low-privilege resource service. A normal worker cannot write the resource, its journal, its fence or its receipts. A filesystem path or repository URL alone is not identity. The resource service must verify its actual root/repository identity and incarnation, with the external restore trust anchor described below.

The proposed authorization linearization point is the protected resource service's final conditional acceptance **immediately before its native conditional publication**, while it holds the resource's exclusive mutation/fence gate. It has staged and validated exact immutable input, checked the actual resource state and a conservative deadline, and irreversibly reserved this operation in its durable resource journal. It retains exclusive mutation ownership through the native result and receipt recording. If the platform cannot prove that untrusted or competing writers cannot interleave between that acceptance and native CAS, the operation remains denied. The final acceptance is a new contract point, not PostgreSQL COMMIT or response delivery.

The domain-separated, bounded descriptor and its independently authenticated envelope must bind all of:

| Binding | Required value |
| --- | --- |
| Operation | protocol/version, operation UUID, action ID, fixed action, exact payload byte count and SHA-256; no normalization after authentication |
| Authority | source/target authority UUIDs, external authority incarnation, ownership generation, validated canonical snapshot gate revision and catalog certificate/context digests |
| Host and actor | independently pinned host/key fingerprint, monotonic host epoch, exact worker/capability and coordinator/verifier identities |
| Reviewed context | exact request, claim, proof and ticket/context digests, not-before times and the minimum immutable expiry |
| Canonical work | run/project/version/status, branch/base/head SHAs, complete valid catalog, retained target project lane and WIP at most two |
| Resource | actual resource UUID/incarnation, current local fence, exact path or fixed ref, expected version/state/ref and exact intended result |

The trusted verifier still validates signatures and complete canonical history; a client cannot nominate the verifier role or attest its own digest. Intent preparation must be a fixed operation that validates current authority and reserves a fresh action exactly once, bound to this resource operation. A ticket already consumed for diagnostic purposes denies; it cannot be upgraded. The current resource ref/state is read by the protected owner and independently compared to the descriptor. A registered diagnostic context or previously consumed action is never accepted as operation authorization. The snapshot revision identifies the attested read; unrelated nonce/receipt activity does not substitute for checking every authority which can invalidate the effect.

## Fences, current authority and revocation order

A cached policy plus a fresh database nonce does not make an external mutation current. Holding a database connection is also insufficient: connection loss can release its locks while a local process continues. Before enabling an external operation, the implementation must prove a resource-enforced ordering for **every** canonical, host, key, epoch, claim, request, ownership and global-admission writer that could invalidate it.

The proposed minimum protocol for the first single resource is fence-before-authority-change:

1. The resource owner durably advances its monotonic fence under the same gate that serializes native operations, invalidates older prepared operations, enters a closed pending-change state, and acknowledges the exact resource/incarnation/fence/authority-change identity. At most one authority change may be pending for this first resource. A competing operation is ordered wholly before or after this local fence boundary; no operation can be accepted while the change is pending.
2. Only then may the fixed authority writer commit the related canonical/policy/ownership change under the existing PostgreSQL gate, with expected-old authority CAS and the exact authenticated fence evidence. Old SQL entrypoints must not bypass this requirement. An authority conflict can leave the resource fenced; safety takes precedence over availability.
3. The owner reopens that exact fence only after independently authenticating positive committed evidence of the matching authority change and resulting current state. A stale, failed, superseded or unknown commit leaves it closed; old policy cannot be paired with the new fence during the gap. Resolving a failed change requires explicit reconciliation while the resource stays quarantined. Only afterward can a fresh reviewed operation be prepared against the resulting authority and fence. Preparing it does not authorize a future write. The protected resource owner must independently check its immutable descriptor, current open fence, native CAS, deadline and durable operation reservation at the actual boundary.

No shadow canonical run store is proposed. The resource keeps fence/operation evidence and exact bound digests, while PPO remains the canonical run owner. The existing database-only fence does not yet implement this protocol. A proof that **all relevant writers** participate, including cancellation and emergency stop, is an implementation prerequisite. If a required writer cannot participate, the affected operation denies.

Revocation becomes effective for new effects on that resource when the protected owner durably acknowledges the new fence. A requested or database-recorded revocation is not represented as globally effective before every resource in its declared scope has fenced or been independently disabled. The first pilot should have one resource to avoid an unproven multi-resource fanout protocol. A timeout or missing acknowledgment means `revocation-pending/unknown`, denies further preparation/dispatch, and quarantines that resource; it does not authorize a replacement owner or claim that an unreachable owner has stopped. Authority administrators must not silently bypass the fence while labeling the change effective.

This is an explicit semantic choice requiring owner approval. It defines ordered resource-side effectiveness rather than an instantaneous, cross-store revocation promise. An operation accepted before the fence may already be irreversible. Advancing the fence prevents later acceptance; it cannot undo an earlier effect or guarantee interrupting an in-progress syscall. A resource service which can continue to accept **new** operations after a committed local fence fails this contract.

## Clock and deadline semantics

The resource owner is the deadline enforcement point. It uses a continuous monotonic elapsed-time source plus an independently trusted time anchor with an explicit, measured uncertainty interval. Translation of signed UTC deadlines must conservatively account for anchor age, clock drift, clock changes, suspend/resume and transport delay. At final acceptance, the **upper bound** of possible current time must be strictly earlier than every bound request/claim/proof/operation expiry; the lower bound must satisfy every not-before condition. Equality, missing bounds, uncertain time, excessive anchor age or detected clock regression denies. A new boot/incarnation invalidates old local translations until trusted reconciliation.

PostgreSQL `clock_timestamp()` samples and JavaScript `Date.now()` are not, by themselves, a bounded uncertainty proof or an atomic wall-clock durable-commit clock. A deferred constraint trigger can be forced to execute early with `SET CONSTRAINTS ALL IMMEDIATE`; later transaction work, expiry and COMMIT can follow it. Neither a deferred trigger nor an explicit pre-COMMIT check is an unconditional durable-commit freshness boundary. The proposal does not assume synchronized Mac/VPS clocks. Batch 2 must establish a concrete clock/uncertainty policy before any operation is enabled; a platform unable to supply that policy remains denied. The existing 60-second signed proof ceiling is not widened.

The minimum signed expiry controls **authorization**, not a new deadline to begin unrelated work. Payload staging, authentication, path resolution, object construction, catalog validation and lock waits happen before the final check. No resource permit is returned for use later by another process. Time between acceptance and native CAS is restricted to the bounded fixed critical section; it cannot include model work, a network round trip or an arbitrary child command.

Completion, durability flush, receipt publication and acknowledgment may occur after authorization expiry. Under the proposed condition this would not retroactively invalidate an operation which was safely accepted before expiry; its exact result is recorded as completed, denied or unknown. This is precisely the departure from the original strict contract and is **not currently executable policy**.

For the scratch pilot, propose a maximum permitted critical-section budget of **five seconds**, subject to smaller measured per-operation budgets and explicit owner approval. This is a policy ceiling, not evidence that an OS syscall can be interrupted within five seconds. No action is enabled until Batch 2A measures latency, lock/revocation delay and cancellation behavior and defines its admission, staging, statement, lock, transaction, transport and acknowledgment budgets. If a budget is exhausted before acceptance, deny with no publication. If exceeded after acceptance, request cancellation where safe, quarantine the operation/resource, deny new work and reconcile the exact effect. Do not report successful cancellation until native evidence proves it. An uninterruptible or irreversible effect may outlast the budget and must remain unknown/quarantined; it does not permit another attempt or simultaneous owner.

## Effect, durability and reconciliation

Before dispatch, the coordinator durably retains the exact operation ID, descriptor bytes/digest, intended resource/result and expected predecessor. This journal is recovery evidence, not a credential. The resource owner durably records the same identity before its conditional publication. Resource-native evidence must distinguish this operation from another operation with identical user payload: the scratch artifact format or reviewed Git commit binds the operation UUID. A hash of generic payload bytes alone is insufficient.

One exact operation may produce at most one native effect. Native expected-old/expected-absent CAS, the resource's protected monotonic fence and immutable operation identity enforce that property at the boundary. The resource journal/receipt cannot be edited or deleted by ordinary roles. Database action consumption is retained conservatively and can coordinate intent, but it cannot supply atomicity with an external journal/ref/file. A failed database receipt write after a real effect must never be reported as rollback of that effect.

A crash between native publication and receipt recording is possible unless a separately proven native transaction closes that gap. Reconciliation therefore reads the exact protected resource-native evidence and journal under the current validated incarnation/fence. It may report a positive committed effect only when the operation identity, predecessor, intended result and immutable native evidence agree. A database receipt without that evidence cannot assert an external effect. A resource effect without a finished database receipt remains a real effect needing reconciliation, not permission to repeat it. Missing receipt, missing resource, old snapshots, malformed evidence, disagreement or unavailable storage report `unknown`; absence never proves noncommit. An ambiguous attempt stays latched across client/service restarts. No automatic retry, new-ID duplicate dispatch or permissive fallback is allowed.

A later revocation, canonical change or expiry does not erase a historical committed result or turn inspection into authority. Every response reports an operation status and evidence only. It never contains a reusable execution grant. If repair is necessary, it requires a new explicitly reviewed operation against the proven current resource state; it cannot rewrite history or reuse the old action nonce. The initial create-only artifact cannot be replaced as "recovery," and Git reversal is a separate expected-old CAS operation, not rollback of an acknowledged historical fact.

## Failure and emergency behavior

| Condition | Required behavior |
| --- | --- |
| Authority unavailable before preparation or observed loss before final acceptance | Deny new acceptance; retain exact pending evidence and quarantine uncertainty. No cached broad execution grant. |
| Network partition after preparation | Preparation alone permits no effect. The protected resource fence and deadline remain mandatory. Loss may be detected late; the protocol must not claim an instantaneous partition detector or globally effective stop before resource acknowledgment. Any already accepted operation follows the bounded completion/reconciliation rules. |
| Revocation races operation | The resource gate orders acceptance versus durable fence advancement. Earlier accepted effect may complete; later acceptance using old identity/epoch/fence denies. |
| Process termination before native publication | No effect may be claimed; preserve any consumed nonce and prepared record. Exact inspection is required; absence alone does not authorize reuse. |
| Process termination after publication, lost acknowledgment or database receipt failure | Quarantine and reconcile the exact native operation. No replay or replacement owner based on a missing acknowledgment. |
| Out-of-band ordinary writer or path/ref substitution | OS ownership and native CAS must deny; otherwise the operation is unsupported. Reject symlink/hard-link/root-identity changes using proven platform containment primitives. |
| Backup restore, clone, journal rollback or stale service incarnation | Default quarantine until an external monotonic trust anchor, outside all restored authority/resource rollback domains, admits a new incarnation and reconciles outstanding operations. In-database generation alone is insufficient. |
| Emergency stop | Stop preparing/dispatching; fence the resource and revoke host policy through the same ordered protocol. Report acknowledgment scope and outstanding accepted operations. Do not claim rollback of irreversible effects. |

A bounded prepared intent may arrive after another policy change only if it still matches the protected resource's current fence; otherwise it denies. Delayed acknowledgments cannot clear a newer uncertainty or downgrade a current incarnation. Trust requires protected low-privilege resource ownership, exclusive resource mutation, authenticated/pinned service identities and keys, dedicated transaction connection ownership, rejection of untrusted role switching, and external anti-rollback policy. Privileged host compromise, an administrator bypassing the trusted gateways or unbounded time uncertainty is not solved by a signature. Pilot enablement is denied when those assumptions are not established.

## Comparison with the original contract and approval gate

| Property | Existing strict Phase 1G-A / current laboratory | Proposed protected-resource condition |
| --- | --- | --- |
| Freshness success | Require freshness through the acknowledged nonce grant/commit linearization point; ordinary PostgreSQL samples cannot prove it, so no executable grant | Require conservative freshness at actual protected native acceptance; allow bounded same-operation completion/ack afterward |
| Side effects | Every later effect must independently honor current fences/expiry; B2c2 proves only a same-database synthetic effect | No later transferable grant: exact fixed effect is inseparable from resource-local fence/CAS acceptance |
| Current authority/revocation | Shared PostgreSQL gate serializes database authorities, not a remote filesystem | Every invalidating authority writer must participate in resource fence-before-change ordering; effective revocation scope is explicitly acknowledged |
| Atomicity | Nonce/effect/receipt are atomic for the synthetic database resource only | Native effect has its own boundary; cross-store gaps are explicit and reconcile conservatively, never represented as one transaction |
| Outcome | All grant/execution/release flags false, including a committed synthetic effect | Operation-specific result/evidence, never a reusable grant; enabling any real operation requires separate approved implementation |

Owner approval must identify this document's exact revision and explicitly accept: (1) authorization-before-expiry rather than durable-completion/ack-before-expiry; (2) the stated resource-local revocation ordering and limits of cancellation/partition detection; (3) the concrete clock trust/uncertainty and measured duration policy; and (4) the required protected-writer, transport and external restore assumptions. Campaign authorization, passing CI, approval of a source PR or a document review is not implicit approval of these changed executable semantics. Any unapproved item remains a blocker; do not connect a successful Phase 1F callback as a shortcut. The actual Mac/VPS pilot still needs a separate final authorization.

## Dependencies and evidence required next

Independent offline/disposable work can proceed now: **2A** measure the existing PostgreSQL/Node bounds and set conservative capacity/retention budgets; **2B** implement pinned synthetic service identities, verifier/consumer/admin separation, bounded transports and uncertain-connection disposal; **2C** prove quarantine and external monotonic incarnation anchoring against restore/clone, nonce reuse, host revival and concurrent owners. These do not authorize execution or relax this approval gate. The 20-run laboratory ceiling and finite certificate/nonce/receipt histories must be an explicit retention/capacity decision, not an unnoticed production lifetime limit; no pruning/reset is approved here.

**2D depends on owner approval of this contract and successful 2A/2B/2C prerequisites.** Its disposable proof must cover every invalidating authority writer, protected native identity/path/ref ownership, symlink and competing-writer attacks, CAS/replay, current host/epoch/ownership, fence-before-change ordering, time uncertainty/expiry, partition/loss, cancellation, process kill/restart, restore quarantine and exact positive reconciliation through every crash gap. If a candidate native primitive cannot enforce the invariant, keep that operation denied rather than expanding to a generic executor.

Synthetic migration/quiescence rehearsal and pilot configuration/emergency-procedure preparation may proceed offline against these explicit dependencies. Actual source/resource use, host connectivity/enrollment, live credentials, remote dispatch, production routing/migration/deployment, real factory cycles, abandoned-run retirement, RIC-59/RIC-61 hold release and a real PPO cutover remain unauthorized. The eventual consolidated review must contain the approved contract revision, exact merged inventory, independent test and seven-gate evidence, review dispositions, cross-component invariants, measured limits, native resource/restore/recovery proof and an explicit pilot go/no-go; a ready harness is not production approval.
