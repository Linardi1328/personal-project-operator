## Goal

Prove that PPO can complete useful internal work for the owner on one real project,
then broaden one reviewed boundary at a time. Preserve GitHub as the canonical code
record, PPO as the execution/evidence authority, exact-SHA tests and review, bounded
remediation, and explicit owner authority for any release.

Stage 3 is not public SaaS. It does not authorize external users, tenant onboarding,
billing, teams, shared credentials, automatic production deployment, unrestricted
provider access, or a dashboard.

## Pilot decision

KHLIM Assist is the first pilot because the tracked project record marks it high
priority, the fixed registry and runtime profile already include it, and its current
task is a bounded regression-test addition. Participant auto-replies remain disabled.
This makes the first real task useful while limiting operational impact.

The pilot does not prove frontend coordination because its first task is backend/test
work. Antigravity and Vercel remain separate later gates. No second project is selected
until the KHLIM Assist pilot evidence is reviewed.

## Stage 3A — pilot readiness observation

Add a read-only readiness boundary fixed to KHLIM Assist. It may inspect only the
approved registry entry, reviewed runtime/tool policy, canonical source checkout,
exact revision and cleanliness, required local dependencies, GitHub read-only facts,
and the required validation workflow. It emits bounded PASS/FAIL/SKIP observations.

It must not create or mutate a run, workspace, branch, issue, pull request, provider
session, preview, deployment, production resource, credential, or customer message.
Missing remote/host facts remain SKIP or FAIL; policy parity cannot convert them to
PASS.

Exit evidence:

- fixed project/repository identity and no caller-selected target;
- clean canonical checkout at an observed exact SHA;
- approved runtime, tools, test policy, and host dependencies available;
- required GitHub validation workflow observed read-only;
- metadata-only bounded report with no paths, credentials, logs, or arbitrary output;
- deterministic refusal coverage for unknown, mismatched, dirty, missing, and stale
  observations.

## Stage 3C — Antigravity frontend adapter verification

Implement its provider adapter only as a separate reviewed increment after the owner
provides an approved local integration boundary. Credentials remain owner-managed and

## Stage 3D — contract-first frontend/backend coordination

Select a frontend-bearing project only after 3C passes. Define a reviewed interface
contract before either provider edits code. Codex owns approved backend scope;
Antigravity owns approved frontend scope. Work remains sequential in Stage 3: no parallel
RunUnits, shared mutable workspace, or cross-provider credential access.

Each handoff binds project, base SHA, interface-contract hash, allowed paths, provider,
tests, and resulting SHA. Conflicts, stale contracts, unexpected files, or incompatible
SHAs require owner action. Both scopes receive exact-SHA tests and independent review
before delivery.

Exit evidence:

- one reviewed interface contract and deterministic ownership of file/scope boundaries;
- successful sequential handoff without hidden fallback or cross-scope edits;
- integrated tests and independent review on the final combined SHA;
- recorded interventions and remediation without fabricated provider success.

## Stage 3E — Vercel exact-SHA preview verification

Vercel remains disabled until a separate preview-only adapter is reviewed. Bind it to one
approved project and one workspace-owned connection reference. The adapter may create or
observe only a preview for the reviewed exact SHA; it must not promote production, change
domains, alter environment variables, or accept caller-selected projects or targets.

Verify the preview URL and deployment SHA through bounded read-only provider facts and an

Exit evidence:

- adapter and authentication readiness tests passed on the approved host;
- preview belongs to the fixed project and exact reviewed SHA;
- approved smoke checks passed with bounded metadata-only evidence;
- production promotion remains unavailable and owner-controlled.

## Stage 3F — owner-approved exact-SHA production pilot

Production is a new separately reviewed authority boundary, not a consequence of merge or
preview success. Add it only after 3A–3E evidence is accepted. Require a fixed per-project
deployment profile, exact previewed SHA, current review and CI, explicit local owner
confirmation, read-only post-deploy verification, and a tested rollback plan.

Ordinary `/ppo continue` must still stop at `merged` unless a later reviewed design
explicitly changes that contract. No automatic release, latest-branch deployment, provider
fallback, or model-selected target is allowed.

Exit evidence:

- one explicitly owner-approved production pilot at the previewed exact SHA;
- bounded deployment and verification evidence tied to the fixed project;
- rollback readiness and ambiguous-write reconciliation tested before use;
- no inference that other projects or providers are production-ready.

## Stage 3G — broaden and evaluate

After the first pilot is reviewed, add projects one at a time. Each project must close its
own runtime, workflow, provider, preview, and release observations; an untested project
remains SKIP and gains no authority from another project's PASS.

Use the Stage 2 read-only projection to summarize recorded task outcomes, attempts,
remediation, durations, and explicit owner interventions. Record cost only from bounded
provider billing evidence; otherwise cost stays unknown. Do not collect prompts, source,
task bodies, raw logs, tokens, or credentials.

Stage 3 completion requires an owner-approved target cohort, reviewed real-task evidence,
zero required SKIP for the exercised boundaries, resolved security findings, and an owner
decision on whether the internal workflow demonstrates enough value to consider Stage 4.
Task count alone is not success.

## Execution protocol

Implement one subphase at a time. Each increment follows implementation, exact-SHA fixed
tests, independent review, bounded remediation, CI, reviewed delivery, and separate owner
acceptance where live host/provider/preview/production evidence is required. Stop on
ambiguity and reconcile through existing APIs. Never self-approve an independent review,
invent PASS evidence, or weaken a prior boundary to advance the roadmap.
